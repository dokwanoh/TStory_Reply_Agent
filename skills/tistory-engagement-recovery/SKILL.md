# 티스토리 확산 복구와 인계

## 원장과 연결 확인

1. 사용자 프로젝트의 `AGENTS.md`, 비공개 `BROWSER_SETUP.md`, `.local/state/connection.json`을 읽는다. [CLI 계약](../tistory-engagement/references/ledger-cli.md)의 `status`로 열린 run, pending, 활성 session을 확인한다.
2. 현재 브라우저 도구 문서를 읽고 최신 브라우저 목록에서 **Chrome ‘티스토리 확산봇’**의 프로필명과 확장 식별자를 모두 대조한다. 숫자 브라우저 ID를 영구 ID로 믿지 않는다.
3. 로그인된 티스토리 블로그가 비공개 설정의 계정인지 실제 화면에서 확인한다. 지정 계정이 아니거나 확인할 수 없으면 멈춘다.
4. 해당 프로필 안에서만 탭을 읽고 조작한다. 기본 Chrome, 게시봇, 내장 브라우저, 새 프로필, 전역 키보드·마우스로 대체하지 않는다.
5. 로그인 만료는 이 전용 프로필에서 정상 재인증한다. 비밀번호·쿠키·인증 파일·서명 URL을 채팅·원장·Git·다른 프로필에 복사하지 않는다. 기존 키체인 참조만 사용한다. CAPTCHA·OTP 등 사람 확인이 필요하면 실제 화면을 근거로 요청한다.

## 중단 예약

- pending 예약부터 실제 화면의 작성자·댓글 전문·구독 상태·공감 상태와 대조한다.
- 확실한 성공은 원래 attempt의 `finish confirmed`, 결과를 알 수 없으면 `finish uncertain`으로 닫는다.
- `not_submitted`는 **외부 전송이 없었음을 입증할 수 있을 때만** 쓴다. 실패 문구나 네트워크 오류만으로 미전송을 단정하지 않는다.
- 이미 닫힌 uncertain 영수증을 confirmed로 덮어쓰거나 새 예약으로 재전송하지 않는다. 추가 관찰은 비공개 인계 보고에 남긴다.
- STOP·pending·중복 방지 기록을 삭제해 통과시키지 않는다. 실제 상태를 확인할 수 없으면 그 지점에서 멈추고 보고한다.

## 동일 작업 3회 연속 실패

- 읽기 작업 또는 전송 전 실패임이 증명된 작업만 `session-failure`로 센다. `operation`은 같은 의미의 고정 키를 유지한다. 오류 문구를 바꿔 카운터를 피하지 않는다.
- 성공을 실제로 확인하면 `session-success`로 연속 실패를 초기화한다. 외부 행동 confirmed도 카운터를 초기화한다.
- **같은 작업이 3회 연속 실패하면 기존 작업기의 브라우저 호출을 중단한다.** 세 번째 실패는 원장에 `handoff_required=true`와 소유권 해제로 저장되어 기존 session의 새 예약을 막는다.
- 마지막 URL·단계·실패 원인·예약/영수증·다음 행동을 기록하고 `report`로 인계 요약을 만든다. run ID와 최초 목표는 유지한다.
- 새 작업기는 **새 브라우저 자동화 런타임/실행 문맥**이다. 실제로 이전 작업기를 멈춘 뒤 런타임을 새로 초기화하고 문서를 다시 읽어 전용 프로필과 계정을 재확인한다. owner 문자열만 바꾸고 같은 실패 문맥을 계속 쓰지 않는다.
- 새 문맥의 실제 식별자를 owner로 `session-start`하고 동일 run을 이어간다. 새 Chrome 프로필이나 별도 보충 run을 만들지 않는다. 이전 작업기와 병렬 실행하지 않는다.
- 현재 도구가 새 실행 문맥을 만들 수 없다면 인계 필요 상태와 이유를 보고한다. 새 작업기가 실행됐다고 꾸미지 않는다.

## 재개와 종료

- 최초 article 관찰값은 보존한다. 현재 화면 상태와 기존 confirmed 영수증이 충돌하면 클릭하지 않고 대조부터 한다.
- 확산을 이어갈 때 [실행 스킬](../tistory-engagement/SKILL.md)로 돌아간다.
- 인계·중단·최종 종료 시 [보고 스킬](../tistory-engagement-report/SKILL.md)을 적용한다.
